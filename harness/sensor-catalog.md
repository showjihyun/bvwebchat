# 센서 카탈로그 — 가드레일 지도 한 장

3층 모델. 위층이 아래층보다 강하다.

- **Guide** — 행동 **전**에 읽는 규칙. 강제력 없음. 어기려면 어길 수 있다.
- **Boundary** — 행동 **자체**를 구조로 막는다. 어길 수단이 없다.
- **Sensor** — 행동 **후** 관찰·교정. 이미 벌어진 것을 본다.

실행 성질: **Comp**(결정론적·빠름) / **Inf**(추론적·느림·비결정).
상태 표기: ✅ 배선 완료·실동작 / 🔄 산출물은 있으나 배선 미완 / ⬜ 미구현.

원칙: "반드시"는 Boundary로, "권장"은 Guide로. 관측만 필요한 것이 Sensor다.
설계 근거 전문은 `docs/harness/architecture-2026.html`.

## Boundary (구조적 통제)

Guide가 "부탁"이라면 이 층은 "불가능"이다. 이 층에 올릴 수 있는 규칙을
Sensor로 두는 것은 낭비이고, 반대로 추론이 필요한 판단을 여기 올리면 오작동한다.

| 통제 | 무엇을 불가능하게 하는가 | 강제 주체 | 상태 |
|---|---|---|---|
| R0/R2/R3 정적 권한 | 관찰은 항상 허용 · 경계 이탈은 사람 승인 · 이력 파괴·시크릿은 거부 | `.claude/settings.json` permissions | ✅ |
| ↳ **R2는 금지가 아니다** | R2는 "묻고 기다려라"가 아니라 **"사람이 보는 앞에서 해라"**다. 승인 채널은 권한 프롬프트 하나뿐이고 **시도하는 행위 자체가 그 채널을 통과시킨다.** 동료 에이전트에게 허락을 구하는 것은 권한 세탁이라 받아도 승인이 아니고, 기다리면 늦은 채널이 아니라 **존재하지 않는 채널**을 기다리게 된다 | `tool-risk.json` R2 `_doc` | ✅ (2026-07-27 `npm ci` 건에서 에이전트 둘이 이 오해로 멈췄다) |
| R1 단계×경로 매트릭스 | RED에서 `src/**` 쓰기, GREEN에서 `tests/**` 쓰기, HARNESS에서 `src/**`·`tests/**` 쓰기 | `.claude/hooks/gate_phase.py` (서브프로세스 0, 예산 ≤150ms) | ✅ |
| 리다이렉트 차단 | `> .harness/state/…` · `> evals/golden/…` 등 통제면 우회 셸 리다이렉트 | `gate_phase.py` + `tool-risk.json` `deny_redirect` | ✅ (탐지이지 예방이 아니다 — `node -e fs.write…`는 못 막는다) |
| 전이 가드 11종 | 직전 단계가 만들지 않은 산출물로 다음 단계에 진입하는 것 | `harness/phase.py enter` | ✅ |
| 골든 정답 수정 승인 | 에이전트가 자기 정답지를 쓰는 것 | permissions `ask` (`evals/golden/**`) | ✅ |
| 강제 전이의 가시성 | `force`를 조용히 쓰는 것 | permissions `ask` + `forced:true` 박제 + 비율 노출 | ✅ |
| 진입점 예산 | `CLAUDE.md` 100줄 초과 (안티패턴 01의 유일한 기계 방어) | `doc-map.json` C5 + `doc-freshness.mjs` | 🔄 스크립트 ✅ / CI 배선 미완 |

`gate_spec_freeze.py`는 삭제됐다. 🟡이 0건이라 영구 no-op이면서 매 Write마다
파이썬 프로세스를 붙였다. 기능은 `PLAN→RED` 가드 `no_pending_spec`이 흡수했다
— 매 쓰기 검사에서 전이 1회 검사로, 메커니즘 2개에서 1개로 줄었다.

**R2는 "묻고 기다려라"가 아니라 "사람이 보는 앞에서 해라"다.** 승인 채널은 Claude Code
권한 프롬프트 하나뿐이고, **시도하는 행위 자체가 그 채널을 통과시키는 행위**다. 동료
에이전트에게 허락을 구하는 것은 권한 세탁이며 받아도 승인이 아니다 — 기다리면 늦은
채널이 아니라 **존재하지 않는 채널**을 기다리게 된다. 2026-07-27 `npm ci` 건에서
에이전트 둘이 이 오류로 멈췄다. 통합에 필요한 것이 정확히 R2이므로
(`git push`·`gh pr create`·`docker`·`npm ci`·`git worktree add`), 이 오해가 규범이
되면 통합 자체가 불가능해진다.

### 이 층의 한계 — **등급 분류는 도구 표면에 걸리고, 스크립트는 도구 표면이 아니다**

`tool-risk.json`은 `git worktree remove`를 R2(사람 승인)로 **올바르게** 분류한다.
그러나 그 분류가 붙는 곳은 **Bash 도구 호출**이다. 우리 스크립트가
`spawnSync('git', ['worktree','remove', …])`로 같은 명령을 부르면 **어떤 등급도
보지 않는다.** 등급표가 틀린 게 아니라 관할 밖이다.

2026-07-27에 이 구멍으로 실제 피해가 났다. `eval-b.mjs`가 워크트리에
`node_modules`를 Windows 정션으로 연결했고, 정리 단계의 `git worktree remove
--force`가 그 정션을 **따라가** 원본을 지웠다. 저장소의 모든 lint·test·build가
멈췄다.

**정정해 둘 것** (실측):

| 호출 | 정션 통과 |
|---|---|
| `rmSync(dir, {recursive:true, force:true})` | **안 따라간다** — unlink만 한다, 원본 보존 |
| `git worktree remove --force` | **따라간다** — 원본 파괴 |
| 정션을 먼저 unlink → 그 다음 worktree remove | 원본 보존 |

`rmSync`는 범인이 아니다. 이 구분이 없으면 이미 안전한 곳을 고치게 된다.

계획서 §8-2는 이 구멍을 "Bash가 경계면의 구멍 — `node -e`로 우회할 수 있다"고
**적대적 우회**로 서술했다. 정확한 서술은 위 문장이고, **실제로 그 구멍에 들어간
것은 우리가 커밋한 정직한 코드**였다. 적대적 우회는 드물지만 이쪽은 계속 일어난다.
새 스크립트를 만들 때 **R2/R3에 해당하는 명령을 `spawnSync`로 부르는지**를
보는 것이 현재 유일한 방어다(`harness-audit` 변경 제안 조건에 포함).

## Sensors — S1~S4

핵심은 개수 4가 아니라 **기질이 서로 다르다**는 것이다. 같은 `vitest run`을 네 번
이름만 바꿔 부르면 센서는 하나뿐이다. 각 계열은 다른 질문에 다른 재료로 답한다.

| 계열 | 질문 | 기질 | **이 계열만 잡는 실패** |
|---|---|---|---|
| **S1** 도구 실행 | 행위가 먹혔나? | 도구 호출 결과 (`trajectory.jsonl` v2 · `tools.jsonl`) | "같은 파일 6번 수정", "Edit 3연속 실패" — 테스트는 전부 초록인데 헤매는 중 |
| **S2** 자동 테스트 | 코드가 도나? | 소스 트리 (eslint · `tsc --noEmit` · vitest) | 타입 오류·린트 위반·단언 실패. 타입 전용 변경에서는 vitest가 눈이 멀고 tsc만이 센서다 |
| **S3** 요구사항 충족 | 스펙이 시킨 걸 했나? | `evals/golden/` | "테스트 전부 통과인데 GA-22에 해당하는 테스트가 **아예 없다**" — S2로는 원리적으로 관측 불가 |
| **S4** 변경 영향 회귀 | 다른 게 깨졌나? | Docker 아티팩트 · 반복 실행 분포 · git 이력 | 번들·컨테이너에서만 깨짐(esbuild ≠ Vite), ~1/10 flake — 단발 실행으로 관측 불가 |

### S2 — 자동 테스트

| 이름 | 실행 | 배치 | 강제 수단 | 상태 |
|---|---|---|---|---|
| 파일 수정 후 빠른 검사 | Comp | 수정 직후 (PostToolUse) | `post_observe.py` → `node scripts/check.mjs --fast` | ✅ |
| lint / typecheck / 단위·통합 테스트 | Comp | CI PR 게이트 | `ci.yml` → `check.sh` → `node scripts/check.mjs` | ✅ |
| 전체 검증 전이 가드 | Comp | `GREEN→EVAL` | `check_full_green` 가드 (`check.mjs` exit 0) | ✅ |
| Red 정당성 판정 | Comp | `RED→GREEN` | `red_evidence` 가드 → `check.mjs --red --rq` (ADR-0005 결정3: TS2307/TS2305만 정당한 Red) | ✅ |

**`--fast` 실측 (2026-07-27)**: 변경 파일 5개 기준 0.72–0.84초 (`--cache` 웜, 3회 측정).
ADR-0005 결정5의 예산은 5초이고, 초과 시 실패가 아니라 경고를 낸다.
이전 카탈로그의 "1.4초"는 `.tsx`·`.mjs`가 린트 대상에서 빠져 있던 시절의 수치라
비교 대상이 아니다 — 그 구멍이 클라이언트 10개 파일과 `scripts/` 센서들을
훅 경로에서 보이지 않게 했다. 대상 파일 수에 비례하므로 단일 상수로 인용하지 않는다.

이 계열의 상한은 `evaluator` 하나에 걸려 있다. 추론 센서를 결정론으로 위장하지 않는다.

### S4 — 변경 영향 회귀

| 이름 | 실행 | 배치 | 강제 수단 | 상태 |
|---|---|---|---|---|
| 배포 아티팩트 빌드 + 골든 스모크 | Comp | main 머지 → 배포 | `deploy.yml` → Docker 빌드 → `smoke.sh`(health + GA-01 + GA-04) | ✅ (2026-07-21 기준 최근 5회 연속 성공 — `gh run list --workflow=deploy.yml`) |
| flake 시그니처 수집 | Comp | 리팩터 전후 · 의심 시 | `check.mjs --repeat N` — `assert`/`collect`/`crash` 3모집단 분류 | ✅ 수동 호출 |
| git 이력 재유도 (단계 순서 대조) | Comp | CI | `phase-audit.mjs [--base <ref>] [--all] [--strict]` — Bash 우회의 **탐지** 경로(예방이 아니다). 인자 없으면 `origin/main...HEAD` 범위, 저장소 전체는 `--all`. **기록과의 모순만** 차단하고 이력 자체의 이상은 advisory(`--strict`로 승격) | 🔄 스크립트 ✅ / CI 미배선 |
| 재개 시험 (L3 졸업 시험 · GB-06) | Comp | 상태 계약 변경 시 | `resume-test.mjs --cold` — worktree 격리 + `claude -p` 5문항 채점 (정답지 = 체크포인트 파일 자체) | 🔄 스크립트 ✅ / **첫 통과 미확인** |

배포 후 스모크의 🟡는 해제됐다. RQ-05/RQ-17이 종결됐고 `deploy.yml`·`smoke.sh`가
실제로 초록이다. 컨테이너는 S4의 **유일한 실환경 기질**이다 — `vitest`는 Vite로,
배포 아티팩트는 esbuild로 해석하므로 초록 vitest가 빌드를 증명하지 않는다.

flake 판정 기준은 횟수가 아니다. 같은 코드가 동시 실행 에이전트 수에 따라 다른
숫자를 낸다(에이전트 1개: 9/10 통과, 4~5개: 3회 중 2회 크래시). 기준은
**"단언 레벨 실패 0건 + 모든 실패가 워커 크래시 시그니처"** 이고, 여기에
"테스트 수·파일 수 정확 일치 + pending suite 0"을 더한다 — *조용히 건너뛴 스위트*는
"리팩터가 테스트 로드를 깨뜨렸다"와 실패 모양이 구별되지 않기 때문이다.

| changelog 동행 | Comp | `HARNESS→REVIEW` 전이 | `changelog_updated` 가드 | ✅ |

**테스트 없는 게이트는 연극이다.** 훅이 조용히 죽어 항상 allow를 반환하는 상태와
정상 동작하는 상태는 `hooks-selftest` 없이는 구별되지 않는다. 실제로 이번 재구성
중 `gate_spec_freeze.py` 삭제와 `settings.json` 재배선 사이의 창에서 모든
에이전트의 Write/Edit이 죽었고, 그것은 정책 거부가 아니라 훅 파손이었다.
`settings.json`이 참조하는 훅 파일의 실재 검사가 이 스크립트의 필수 단언이다.

### 디스패처 전환의 교환 조건 — 이 절이 여기 있는 이유

`settings.json`은 이제 훅을 직접 부르지 않고 디스패처를 거친다
(`python .claude/hooks/hook.py <handler>`). 파일 참조가 6개에서 1개로 줄어
드리프트 표면이 작아졌다. **대가가 있다**:

| | 직접 배선 (이전) | 디스패처 (현재) |
|---|---|---|
| 핸들러 파일 부재 | python이 exit **2** → 훅 프로토콜에서 **도구 차단** | 디스패처가 경고 후 exit **0** → **통과** |
| 증상 | 저장소 마비 — 누구나 즉시 안다 | **무증상** |
| `hooks-selftest` 출력 | `hook.py`를 **고아 훅**으로 경고 | 참조 스크립트 6개(디스패처 1 + 핸들러 5) |

마지막 행이 이 표를 **자기 한정적**으로 만든다. 직접 배선으로 되돌리면
`hooks-selftest`가 `hook.py`를 다시 고아로 잡고 디스패처 문구는 스스로 사라진다
— 즉 **배선 형태가 바뀌면 경고 문구도 따라 바뀌므로**, 되돌린 상태에서 "무증상이니
이 검사가 유일하다"고 잘못 주장하게 되는 일이 없다. 센서가 자기 전제를 함께 검사한다.

즉 **부재의 실패 양식이 "요란한 마비"에서 "조용한 통과"로 바뀌었다.** 이전에는
배선이 깨지면 저장소가 멈춰서 사람이 자동으로 알았지만, 지금은 아무 일도 일어나지
않는다. **그 계열의 탐지 책임이 전적으로 `hooks-selftest`로 넘어왔다** — 이
층에서 유일한 센서다. 그래서 이 검사를 CI blocking으로 올리는 것이 선택이 아니다.

이 교환은 옳다. fail-OPEN이 아니었으면 새 matcher가 Bash까지 포섭하는 순간
복구 경로가 사라진다. 다만 **대가를 적어 두지 않으면 다음 사람이 대가를 모른 채
센서를 지운다.**

**메타 센서가 실제로 잡은 것 (2026-07-27, 이 재구성 중)** — 이 층이 장식이
아니라는 실증이다. 넷 다 **사람이 아니라 린터가 먼저 발견**했다.

| 센서 | 잡은 것 | 이후 |
|---|---|---|
| `doc-freshness` C4 | 스킬 문서 3개가 **존재하지 않는 스크립트를 부르고 있었다**. 오케스트레이션 스코프 누락(센서 6종만 배정했는데 계획은 8종)이 문서 린터에서 드러났다 | 해소 |
| `policy-lint` P8 | `no_pending_spec` 가드의 정규식이 **문법은 맞고 의미만 죽어** 어떤 입력에도 매칭되지 않았다 — 영구 no-op이라는 이유로 지운 훅의 기능을 흡수한 가드가 다른 이유로 똑같이 no-op였다 | 해소 |
| `hooks-selftest` | `hook.py`가 디스크에 있는데 `settings.json`이 부르지 않는 **고아 훅**. 최악의 경우 "이미 막고 있다"는 착각을 만든다 | 해소 — 그 파일이 디스패처로 배선되며 실참조가 됐다 |
| `metrics.mjs` | 자기 처방으로 "`hooks-selftest`를 CI blocking으로" 를 권고했다 — **학습 루프가 처방을 낸 첫 사례**다 | 미이행 (W4) |

다섯 번째는 성격이 다르다. `metrics.mjs`가 세는 M8을 **잘못된 술어로 읽으면**
`warn_only === false`가 0건을 내고, 그때 정상 동작하는 센서가 "센서 없음"과
구별되지 않는다. 죽은 훅과 엄격한 훅이 침묵으로 구별되지 않는 것과 같은 실패
양식이 한 겹 위에서 반복된 것이다 — **센서를 만드는 것과 올바로 읽는 것은 다른
일이다.**

## 이 센서망이 실제로 잡은 것과 못 잡은 것 (2026-07-27 재구성 1회분)

위 표들은 각 센서가 **무엇을 잡도록 설계됐는지**를 적는다. 이 절은 **실제로
무엇을 잡았는지**를 적는다. 둘은 같지 않았다.

| # | 실패 | 잡은 주체 |
|---|---|---|
| 1 | `settings.json`이 삭제된 훅 참조 → 세션 마비 | 센서 아님 — **실패 자체가 시끄러웠다**(exit 2). `hooks-selftest`는 그때 없었다 |
| 2 | `policy-lint`의 lint 위반이 저장소 게이트를 깸 | ✅ **자동 센서** (`check.mjs --fast`, PostToolUse) |
| 3 | `no_pending_spec`의 서로게이트 패턴 (죽은 가드) | 사람 — **수동 전수 실증**. P1~P7은 전부 통과했고 **P8은 이 발견 뒤에 생겼다**(`aa91071` → `389f49e`) |
| 4 | 디스패처 배선이 경로 추출을 깸 | ✅ **자동 센서** (`hooks-selftest` WARN) — 단 사람이 돌려서 읽어야 했다 |
| 5 | `node_modules` 파괴 | 훅이 잡았으나 **원인을 잘못 지목**했다. 진짜 원인은 자기 보고 + 실측 |
| 6 | M8 혼동 (18은 시도이지 차단이 아니다) | 사람 — 수동 검증 |
| 7 | 비대칭 경고가 자기 해제되지 않음 | 사람 — **자기 주장을 검증하다** 발견 |

**자동 센서가 온전히 잡은 것은 2건(#2·#4)이다.** 나머지는 에이전트가 서로의
작업을 교차 검증하거나 자기 주장을 검증하다 나왔고, #5는 절반만 잡았는데
**그 절반이 하필 틀린 처방을 가리켰다.**

경계가 뚜렷하다. 결정론적 센서가 잡은 둘은 **기계적으로 관측 가능한 형태의
실패**(린트 위반·경로 추출 역전)였다. 죽은 가드·이름 혼동·자기 해제 안 되는
경고는 전부 **의미 층위의 실패**였고 판단이 잡았다.

이것이 계획서 §8-1 *"파이프라인의 상한은 여전히 추론적 센서 하나에 걸려 있다 —
그 이상을 주장하면 거짓이다"* 의 실측이다. **"하네스가 넷을 잡았다"고 적으면
하네스가 실제보다 강해 보이고, 그것은 M8에서 18을 "차단"이라 부른 것과 같은
종류의 과장이다.** 정직한 서술은 이렇다 — 하네스를 짓는 과정이 하네스가 잡아야
할 실패를 일곱 번 만들어냈고, **자동 센서가 잡은 것은 둘이며, 그 실패들이 규칙을
낳았다.** 마지막 절이 이 하네스가 박물관이 아니라는 근거이고, 앞의 둘이 그 한계다.

## 운영 규칙

1. 센서는 가능한 한 왼쪽(수정 직후 > 전이 > pre-commit > CI > 리뷰)에 배치한다.
2. 센서 에러 메시지에는 "어떻게 고치는지"를 담는다 — 에이전트가 읽고
   자기 교정하는 것이 목적이다.
3. 같은 실수가 2회 반복되면: 그 실수를 잡는 센서를 추가하거나,
   Guide 한 줄을 추가한다. (둘 다는 과잉 — 하나만)
4. 분기마다 이 표를 갱신한다. 상태가 전부 ✅면 이 문서가 곧 회고 자료다.
5. **센서를 추가하기 전에, 그 실패를 phase 매트릭스로 구조적으로 불가능하게
   만들 수 있는지 먼저 본다.** 우선순위는 **구조 > 게이트 > 센서 > Guide**다.
   구조로 막을 수 있는 것을 센서로 두면 실패는 계속 일어나고 관측만 남는다.
   반대로 추론이 필요한 판단을 구조로 올리면 오작동해서 결국 꺼진다.
   이 위계의 경험적 근거는 `docs/harness/architecture-2026.html` §00에 있다 —
   이 재구성 중 **규칙을 쓴 사람이 그 규칙을 어긴 사례 4건**이 기록됐고, 그중
   격리된 두 번째 독자가 있던 3건은 산출물이 나오기 전에 잡혔다. **규칙을 아는
   것과 그 규칙 아래에서 매번 옳게 고르는 것은 다른 일이다** — 그래서 Guide가
   위계의 맨 아래다.
5-1. **새 센서의 판정은 종료 코드로 낸다.** 오류를 출력하고 `exit 0`을 반환하면
   그건 센서가 아니라 로그다. 호출자가 `&&`로 엮으면 체인이 안 끊기고, 사람이
   출력을 안 읽으면 아무 일도 일어나지 않는다. 위 4건 중 **유일하게 피해를 낸
   1건**이 이 실수였다(검증 스크립트가 태그 불균형을 출력하고도 `exit 0`을 내
   깨진 문서가 커밋됨). 예외는 의도적으로 비차단인 것뿐이고, 그때는 **왜
   항상 0인지를 헤더에 적는다** — `metrics.mjs`(관측이지 판정이 아니다)와
   `doc-freshness --digest`(세션 시작을 막지 않는다)가 그 예다.
6. **병렬로 파일을 수정하는 에이전트에게는 `git add` 규율이 아니라 워크트리
   격리가 답이다.** 경로 없는 `git commit`은 인덱스 전체를 커밋하므로, 트리를
   공유하는 한 남이 스테이징해 둔 것이 그대로 실린다 — `git add`를 아무리
   조심해도 원리적으로 막을 수 없다. 규칙은 두 겹이다:
   (a) 커밋은 `git commit -- <경로>` 만 쓴다. (b) 애초에 같은 트리를 여러
   에이전트가 쓰게 하지 말고 `isolation: "worktree"`를 먼저 고려한다.
   2026-07-27 이 저장소에서 커밋 귀속 오염이 3회 발생했고(유실 0건,
   `5202196`·`fe61db7` 등) 그만큼 bisect·롤백 granularity가 훼손됐다.
7. **통제면에서 과도한 엄격함은 안전이 아니라 부정확이다.** 정책을 실제보다 좁게
   읽으면(R2를 R3처럼) 또는 게이트를 실제보다 넓게 잡으면(평가 가능한 것을 미리
   차단) 사람은 정책을 우회하는 법을 배우고, 그때부터 정책 **전체**가 신뢰를 잃는다.
   "안전한 쪽으로 틀렸다"는 변호가 안 된다 — 통제면에서 부정확은 그 자체가 위험이다.
   2026-07-27 같은 날 두 사례가 나왔다: `guard_exec`가 `cmd[0] == "node"`를 미리
   막아 stdlib만 쓰는 센서를 거짓 실패시킨 것, 그리고 R2를 사람 지시 대기로 읽어
   에이전트 둘이 멈춘 것. **둘 다 방향이 같다.** `enforce.warn_only`로 유예를 둔
   것도 같은 논리다 — 첫 주에 과차단이 잦으면 `force`가 습관이 되고, 그 순간
   게이트 전체가 장식이 된다.
8. **센서의 출력 기호가 상태보다 적으면 안 된다.** `PASS` 하나가 두 상태를 덮으면
   그 구별이 사람에게 넘어가고, 사람은 결국 안 한다. 2026-07-27 하루에 같은 병이
   **네 번** 나왔고 처방은 넷 다 같았다 — **기호를 늘린다.**

   | 센서 | 한 기호가 덮고 있던 두 상태 | 처방 |
   |---|---|---|
   | `no_pending_spec` | "위반 0건" ↔ **"매칭 능력이 없다"** | 매칭 불가 패턴을 실패로 (P8) |
   | 고아 훅 검사 | "배선 정상" ↔ **"디스패처 뒤의 부재를 못 본다"** | 간접층 추적 + 핸들러 실재 검사 |
   | `policy-lint --print` | "검사 통과" ↔ **"검사를 안 돌렸다"** | `SKIP` 기호 신설 |
   | 스키마 비대칭 경고 | "지금 문제" ↔ **"예전 문제(이미 고침)"** | 시간 순서로 판정, ⚠와 참고를 분리 |

   공통 구조: 오른쪽 칸이 전부 **"센서가 자기 상태를 자기 출력에 반영하지 못한다"**
   이고, 왼쪽으로 붕괴하면 **조용한 통과**가 된다. 조용한 통과는 게이트가 없는 것과
   같으면서 있다고 믿게 만들므로, 게이트가 아예 없는 것보다 나쁘다.
   **다만 이 규칙은 관측 가능한 상태에 대한 것이지 해석에 대한 것이 아니다.**
   질문은 짝으로 물어야 한다:

   - **기호가 상태보다 적지 않은가** — 조용한 통과를 막는다 (위 4건)
   - **기호가 관측보다 많지 않은가** — 없는 정밀도를 지어내는 것을 막는다

   뒤쪽을 빠뜨리면 "기호를 늘려라"로 읽혀서, 로그가 알 수 없는 구별에까지 기호를
   붙이게 된다. 규칙 7과 같은 모양이다 — **'더 많은 쪽'이 자동으로 안전하지 않다.**

   경계 사례가 `phase-audit`의 "HARNESS 단계에 GREEN 커밋" 이다. 관측은 하나뿐이고
   (그 구간에 그 쓰기가 있었다), 그것이 정당했는지는 **관측이 아니라 판단**이다.
   그래서 이 센서는 기호 하나(FAIL)를 내면서 선택지 둘을 제시하고 고르기를
   거부하며, **고를 근거가 로그에 없다는 사실 자체를 출력에 적는다.** 규칙 8이
   막으려는 것은 "구별할 수 있는데 안 한 것"이지 "구별할 수 없는데 안 한 것"이
   아니다. 후자에 기호를 붙이면 그건 추론을 구조로 올리는 것이고 규칙 5가 막는다.

   **종료 코드도 기호다.** 부작용 있는 명령의 exit 0은 "성공했다"이지 "무엇을
   했는가"가 아니다 — `--print`의 exit 0이 "재생성함"과 "이미 최신"을 함께 덮는다.
   그 구별은 stdout에만 있으므로, 부작용 있는 명령의 출력을 버리면서 종료 코드만
   보는 것은 **기호를 스스로 지우는 행위**다. 2026-07-27 실제로 그렇게 오진했다.

   새 센서를 만들 때 물을 것: **이 센서가 낼 수 있는 기호가, 이 센서가 처할 수 있는
   상태보다 적지 않은가. 그리고 이 센서가 실제로 관측할 수 있는 것보다 많지 않은가.**

   **규칙 5-1은 이 규칙의 특수한 경우다** — 종료 코드는 기호가 둘뿐인 채널이고,
   오류를 출력하면서 `exit 0`을 내면 그 하나가 "통과"와 "오류는 있지만 안 막음"
   두 상태를 덮는다. 위 표의 다섯 번째 행인 셈이다(2026-07-27 검증 스크립트가
