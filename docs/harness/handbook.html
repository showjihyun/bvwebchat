만든 것과, 만드는 방법

앞의 제품 절은 사내 공유용 실시간 채팅 서비스가 어떻게 동작하는지를 그린다 — React 클라이언트와 Socket.IO 서버를 한 Node 런타임에 묶은 단일 컨테이너다.

뒤의 하네스 절은 그 제품을 만든 개발 공정 자체를 그린다. 설계 명제는 하나다 — 구조 > 게이트 > 센서 > Guide. 구조로 불가능하게 만들 수 있는 것을 센서로 두면 실패는 계속 일어나고 관측만 남고, 반대로 추론이 필요한 판단을 구조로 올리면 오작동해서 결국 꺼진다.

Part I

제품 — 실시간 채팅 서비스

채널(room) 참여 채팅과 전체 공지용 global 채널(공지는 참여 중인 각 방 안에도 출처 표시와 함께 뜬다 — RQ-04 v1.2 · ADR-0009), 새로고침 후 세션 복구, 서버가 소유하는 식별과 기본 입력 검증을 최소 구성으로 제공한다. 상태는 전부 프로세스 메모리에 있고 서버 재시작 뒤 영속 복구는 없다 — 그 선택의 대가는 P6 에 적었다.

운영 특성

01
단일 컨테이너빌드된 정적 파일과 Socket.IO 서버가 같은 프로세스·같은 포트를 쓴다 (ADR-0006).
02
서버 소유 식별닉네임 충돌을 서버가 해소하고 불투명 세션 토큰(randomUUID)으로 재연결을 처리한다.
03
입력 검증소켓 이벤트의 이름 필드(nickname·room·token)를 서버가 타입 검사하고 비어 있지 않은지 본다(validation.ts). message 의 본문은 서버가 검사하지 않는다 — 비어 있지 않음을 보는 것은 클라이언트뿐이다(Composer.tsx). 상한은 없다 — 길이·빈도·채널 수 제한을 두지 않았다. 사내 신뢰 경계 안이라는 전제이고, 그 대가는 P6 에 적었다.
04
인메모리 상태영속 저장소가 없다. 재시작하면 이력과 세션이 사라진다 — 사내 공유 용도에 맞춘 선택이다.
P4

연결 수명주기

ADR-0003 · 서버 권위
1접속

브라우저가 Socket.IO 연결을 연다. 접속 즉시 global 에 자동 참여하며 나갈 수 없다(ADR-0004).

2identify

서버가 닉네임을 고유화하고 세션 토큰 · 기본 상태를 ack 으로 돌려준다. 클라이언트는 토큰을 localStorage 에 둔다.

3join / activeRoom

사용자가 room 에 참여하고 지금 보고 있는 채널을 서버에 통지한다 — 안 읽음 계산의 기준점이다.

4message / unread

서버가 room 멤버에게만 메시지를 방송하고, 활성이 아닌 room 에는 unread 를 유니캐스트한다.

5resume

새로고침·일시 단절 뒤 30초 유예 안에 같은 토큰으로 재접속하면 참여 room · 활성 채널 · 안 읽음 수 · 참여자 목록이 되살아난다.

유예 30초의 값. 그 안에 돌아오면 퇴장 처리가 아예 실행되지 않는다 — 다른 참여자 화면에서 사람이 나갔다 들어오는 깜빡임이 없다. 유예가 지나면 정식 퇴장으로 확정되고 빈 user room 은 삭제된다(global 은 예외로 존속).

이벤트 계약

chat/protocol.ts
이벤트내용응답 형태
identify닉네임을 서버에서 확정하고 세션 토큰을 받는다ack

resume30초 유예 안에 세션 컨텍스트를 재바인딩한다ack
ack 이 UI 변경의 기준점이다. 낙관적 표시를 하더라도 서버가 거절하면 되돌린다 — 서버에 없는 room 이 화면에만 남는 유령 상태를 만들지 않는다. 중복 join 은 멱등이고, global 은 자동 참여이며 나가기 UI 자체가 없다 (거짓 어포던스 금지).
global 은 참여자 목록을 갖지 않는다 (ADR-0008). 모든 사용자가 자동 접속돼 있어 참여자를 따로 집계하지 않는다 — UI 는 빈 칸을 두지 않고 그 이유를 표시한다. 이 예외는 global 이 "멤버 0이면 삭제" 경로에 구조적으로 걸리지 않게 하는 보장이기도 하다.
P6

가드레일과 한계

알고 감수하는 것
INPUT
문자열 길이 상한 없음

닉네임 · room 이름 · 메시지 본문에 길이 상한이 없다. 이름 필드의 검사도 타입과 비어 있지 않음 수준이다 — 닉네임만 공백을 거부하고 room 이름은 공백도 통과한다(isNonBlankString 대 isNonEmptyString). 본문은 §P3 대로 서버 검사가 없다. 예약 room 이름 차단과 닉네임 충돌 해소는 별도로 있다. 클라이언트는 닉네임 최소 2자를 본다(DESIGN.md §5). 긴 본문 하나가 그대로 전파된다.

RATE
메시지 빈도 제한 없음

전송 빈도를 제한하지 않는다. 루프를 도는 클라이언트 하나가 채널을 채울 수 있다.

SCOPE
채널 수 상한 없음

세션이 참여할 수 있는 room 수에 상한이 없다. global 은 모두가 자동으로 들어가는 기본 채널이다.

STATE
메모리 한계

채널별 최근 이력 50개. 재시작 뒤 영속 복구 없음.

RESUME
새로고침 뒤 대화가 빈다

서버는 room 이력을 갖고 있는데 클라이언트가 재접속(resume) 후 그것을 요청하지 않는다 — 새로고침하면 그 방이 통째로 빈 채로 보이고, 누군가 새 메시지를 보내야 그때부터 쌓인다. global 사본도 같다. RQ-11·RQ-04 v1.2 가 공유하는 미이행이고 docs/progress.md 보류표에 기전·처방 후보가 있다.

이것은 사내 공유용이지 다중 인스턴스 서비스가 아니다. 상태가 전부 프로세스 메모리에 있으므로 수평 확장이 불가능하고, 프로세스가 죽으면 이력과 세션이 사라진다. 영속화와 다중 인스턴스는 지금 범위 밖이고, 필요해지면 그것은 새 ADR 이 먼저다.

Part II

하네스 — 규칙을 문장이 아니라 구조로 갖는다

아래 14개 절은 구조 > 게이트 > 센서 > Guide 라는 위계가 실제 파일 · 훅 · 게이트로 어떻게 착지했는지를 그린다. 이 하네스가 위의 제품을 만들었고, 제품보다 이쪽이 훨씬 크다.

01

개요 — 3층 모델

harness/sensor-catalog.md

가드레일은 행동에 대한 시간축으로 세 층이다. 위층이 아래층보다 강하다. 원칙은 짧다 — "반드시"는 Boundary 로, "권장"은 Guide 로, 관측만 필요한 것이 Sensor 로.

Boundary가장 강함
행동 자체를 구조로 막는다. 어길 수단이 없다. 단계×경로 매트릭스, 전이 가드, permissions deny, 리다이렉트 차단.
행동 시점시도가 거부된다
Sensor
행동 후 관찰·교정. 이미 벌어진 것을 본다. S1 도구 실행 · S2 자동 테스트 · S3 요구사항 충족 · S4 변경 영향 회귀 + 메타 센서.
행동 후feedback
Guide가장 약함
행동 전에 읽는 규칙. 강제력 없음 — 어기려면 어길 수 있다. CLAUDE.md, specs/requirements.md, ADR, SessionStart 다이제스트, exit_hint.
행동 전feed-forward

세로 순서는 강도이고 오른쪽 칸이 시점이다 — 둘은 같은 축이 아니다. 가장 강한 층이 가장 이른 층은 아니라는 것이 이 표의 요점이다.

진실 공급원 — 충돌하면 위가 이긴다

순위원천관할

2docs/adr/ (0001–0008)아키텍처 결정. 모순 구현 금지 — 변경은 새 ADR 이 먼저다.

위계의 경험적 근거. 재구성 1회분에서 규칙을 쓴 사람이 그 규칙을 어긴 사례 4건이 기록됐고, 격리된 두 번째 독자가 있던 3건만 산출물 전에 잡혔다. 규칙을 아는 것과 그 규칙 아래에서 매번 옳게 고르는 것은 다른 일이다 — 그래서 Guide 가 맨 아래다.
02

단계 상태 머신

harness/policy/phase-matrix.json

작업은 항상 한 단계 안에 있고, 단계가 쓰기 가능한 경로를 정한다. 상태의 유일한 writer 는 harness/phase.py 다. 합법적인 간선이라도 직전 단계만 만들 수 있는 산출물을 가드로 요구한다 — 단계를 뒤집는 것은 막을 수 없지만, 뒤집어도 얻는 게 없다.

각 단계 위의 회색 칩은 그 단계에서 다음 단계로 나가는 전이 가드다. 파란 실선이 행복 경로, 점선이 되돌림, 청록이 하네스 분기다. HARNESS 는 "하네스·ADR 전용 PR" 카브아웃을 구조로 승격한 단계로, 기능 코드가 섞이는 것이 물리적으로 불가능하다.

이 유예의 판정 기준. force 비율이 5%를 넘으면 에이전트가 아니라 이 매트릭스가 틀렸다는 신호다. 통제면에서 과도한 엄격함은 안전이 아니라 부정확이다 — 과차단이 잦으면 force 가 습관이 되고, 그 순간 게이트 전체가 장식이 된다. 그래서 force 는 사유 필수 · forced:true 로 이력에 박제 · 주간 리포트 최상단 노출이다.

전이가드판정 대상 · 요지
SPEC→PLAN no_pending_spec specs/requirements.md 의 🟡 PENDING 이 0건. 스펙이 모호한 상태의 구현은 추측이고, 추측은 재작업이 된다.

GREEN→EVAL check_full_green check.mjs (lint + tsc + vitest) exit 0. 완료 주장에는 실행 출력이 증거로 필요하다.
golden_coverage 통과 여부가 아니라 테스트의 존재 여부를 묻는다. "사양 대조 없는 테스트 통과는 완료가 아니다"의 기계적 집행 지점.
EVAL→REVIEW evaluator_pass 평가 보고서에서 판정: PASS 단독 줄. latest_of 로 판정 줄 중 마지막 것만 본다.
REVIEW→RELEASE reviewer_approve 리뷰 보고서에서 판정: APPROVE 단독 줄. 머지를 막는 마지막 게이트다.
HARNESS→REVIEW track_b_passing 하네스 회귀 평가 아티팩트. 평가셋 없는 하네스 튜닝은 안티패턴이다.

가드가 실제로 깨졌던 두 지점 — 앵커와 범위.
① 앵커 부재: reviewer_approve 의 옛 패턴은 한 줄 안에 "판정"과 "APPROVE"가 함께 나오기만 하면 매칭됐다. REQUEST_CHANGES 를 선언한 보고서가 그 결함을 서술하다가 스스로 게이트를 열 수 있었다 — 결함을 서술하는 행위가 결함을 발동시키는 가드는, 결함을 서술하지 못하게 하는 가드다.
② 범위 부재: 보고서는 회차를 append 하는 규약이라, 파일 전체를 보면 앞 회차의 PASS 가 뒷 회차의 FAIL 을 덮었다. FAIL 보고서가 전이를 열어 준 것이다. 처방은 latest_of — 판정 줄 전부를 찾아 마지막 것만 대조하고, 매칭이 하나도 없으면 실패한다(판정할 수 없는 가드는 없는 가드다).
③ 그 latest_of 도 처음엔 판정 줄을 토큰 하나짜리 줄만 인정해 판정: FAIL — 사유 처럼 꾸밈이 붙으면 안 세어졌다 — 닫았다고 기록한 fail-open 이 절반만 닫혀 있었다. 정의를 넓혀 fail-closed 로 만들었다.

"하네스가 넷을 잡았다"고 적으면 하네스가 실제보다 강해 보인다. 이 파이프라인의 상한은 여전히 추론적 센서 하나에 걸려 있고, 그 이상을 주장하면 거짓이다.

파일성격커밋
phase.json라이브 커서 — 현재 단계 · rq · branch · 서명❌ gitignore
session.json라이브 선언 — 왜 · 완료조건 · 다음 (≤60줄)❌ gitignore

phase.jsonl전이 이력✅ 커밋
왜 상태를 두 수명으로 쪼갰나. 라이브 상태는 자주 바뀌고 커밋 노이즈를 만들지만, 체크포인트는 전이 순간의 스냅샷이라 불변이고 그것이 재개의 정답지가 된다. 그래서 전이는 체크포인트를 만들기 직전에 session.json 의 신선도를 검사하고 낡았으면 전이를 거부한다 — 낡은 채 전이하면 낡은 서사가 박제되기 때문이다.
재개 가능성의 실측 조건은 "앵커 밀도"였다. 체크포인트 서사가 저장소에 실재하는 식별자를 몇 개 담고 있는가가 재개 시험 점수를 갈랐다 — 앵커 풍부 5/5, 앵커 0 이면 3/5(단조). 그래서 policy-lint P12 가 저장소 밖 라벨(리뷰 보고서 내부 기호)을 next·open 에서 찾으면 차단한다 — _workspace/ 는 gitignore 라 신선한 워크트리에 존재하지 않는다.

같은 뿌리의 다른 표면도 있다: 서사가 미추적 파일 경로를 가리켜도 재개가 불가능한데 P12 는 라벨만 보지 경로는 보지 않는다. 실제로 재개 시험이 그것으로 한 번 떨어졌다.

센서 설계 시 물을 것

기호가 상태보다 적지 않은가

한 기호가 두 상태를 덮으면 그 구별이 사람에게 넘어가고, 사람은 결국 안 한다. 왼쪽으로 붕괴하면 조용한 통과가 되는데, 그건 게이트가 없는 것과 같으면서 있다고 믿게 만들므로 아예 없는 것보다 나쁘다.

기호가 관측보다 많지 않은가

없는 정밀도를 지어내는 것을 막는다. 구별할 수 없는데 기호를 붙이면 추론을 구조로 올리는 것이고, 그건 오작동한다.

선언한 기호에 전부 도달할 수 있는가

기호를 둘로 늘렸는데 도달 조건이 "잘못된 모양이 하나라도 있으면" 이면, append-only 로그에서 그 조건은 영원히 참이라 두 번째 기호에 도달할 수 없다.

이 상태가 나중에 다른 뜻이 되지 않는가

처방은 개수가 아니라 순서로 판정하는 것이다 — 그러면 경고가 아무도 손대지 않아도 스스로 꺼진다. 상시 경고는 다음 경고를 무시하게 만드는 훈련이다.

종료 코드도 기호다. 오류를 출력하고 exit 0 을 반환하면 그건 센서가 아니라 로그다 — 호출자가 체인으로 엮으면 안 끊기고, 사람이 출력을 안 읽으면 아무 일도 일어나지 않는다. 예외는 의도적으로 비차단인 것뿐이고, 그때는 왜 항상 0인지를 헤더에 적는다.
