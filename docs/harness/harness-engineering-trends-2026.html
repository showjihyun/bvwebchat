T.01

모델 선택에서 ‘하네스 적합도’ 최적화로

동일 모델의 성능을 얼마나 꺼내 쓰는지가 핵심 변수가 됐다. LangChain은 모델을 고정한 채 시스템 프롬프트·도구·미들웨어를 조정해 Terminal-Bench 2.0 점수를 52.8에서 66.5로 높였다고 보고했다. 2026년 7월 Nemotron 사례도 하네스 튜닝 후 Deep Agents 최고 실행에서 0.86으로 Opus 4.8의 0.87에 근접했고, 실행 비용은 약 $4.48 대 $43.48이었다.

변화의 본질은 “작은 모델이 항상 큰 모델을 이긴다”가 아니다. 과업·도구·시간 예산·검증 방법에 맞는 하네스가 모델의 잠재력을 실제 산출물로 전달하며, 모델 교체 전에 조정할 수 있는 레버가 많아졌다는 뜻이다.

근거: LangChain / Improving Deep Agents · Nemotron 3 Ultra playbook

Decision 모델 벤치마크보다 먼저 ‘현재 하네스 + 현재 과업’의 회귀 평가셋을 만든다.

단, 두 수치 모두 공급자 주도·특정 벤치마크 결과다. 최고 실행값을 평균 성능이나 생산성 ROI로 일반화하지 않는다.

T.02

컨텍스트는 큰 프롬프트가 아니라 ‘탐색 가능한 작업 환경’

장문의 지시문에 모든 지식을 밀어 넣는 방식에서, 짧은 지도와 점진적 공개로 이동한다. OpenAI 사례는 약 100줄의 AGENTS.md를 백과사전이 아니라 목차로 사용하고, 설계·계획·제품 사양·신뢰성 문서를 저장소 안의 버전 관리된 진실의 원천으로 둔다. 문서 최신성도 린터와 주기적 정리 에이전트로 검사한다.

Microsoft Azure SRE 팀의 회고도 같은 방향을 보인다. 2주 만에 100개가 넘는 전용 도구와 정책 매뉴얼형 프롬프트가 생기자 예외와 가드레일이 폭증했고 일반화가 약해졌다. 해법은 모든 것을 전문 도구로 감싸는 것이 아니라, 파일·검색·코드 실행처럼 모델이 이미 잘 다루는 보편적 표면을 제공하는 쪽이었다.

근거: OpenAI / Harness engineering · Microsoft / Context Engineering

Pattern Map → retrieve → verify freshness.

짧은 진입점, 계층형 문서, 리포지토리 검색, 소유자·갱신일·교차 링크 검사를 한 묶음으로 설계한다.

T.03

검증이 사후 QA에서 ‘에이전트의 종료 조건’으로

최신 하네스는 생성이 끝나면 사람이 검사하는 선형 흐름이 아니라, 계획 → 구현 → 테스트 → 사양 대조 → 수정이 루프 안에서 반복되는 구조다. 에이전트가 “코드를 다시 읽고 괜찮아 보인다”고 멈추는 실패를 막기 위해 종료 직전 훅, CI 게이트, 구조적 테스트, 브라우저 조작, 로그·메트릭 질의를 직접 제공한다.

평가의 역할도 점수표에서 개발 피드백으로 바뀐다. 실패 트레이스를 묶어 원인을 분류하고, 하네스 변경을 회귀 평가에 통과시킨 뒤 배포한다. 결정론적 검사가 가능한 곳은 테스트·린터를 우선하고, 의미·취향처럼 계산하기 어려운 부분에만 LLM 평가를 제한적으로 쓴다.

근거: LangChain / Self-verification · OpenAI / Agent legibility & CI · Anthropic / Agent evals

Minimum loop 사양 대조 없는 “테스트 통과”는 완료가 아니다.

도구 실행 성공, 자동 테스트, 원 요구사항 충족, 변경 영향 회귀를 서로 다른 센서로 둔다.

T.04

장기 과업의 핵심은 더 긴 컨텍스트가 아니라 ‘재개 가능성’

수시간·수일 작업은 한 번의 거대한 대화로 버티지 않는다. 계획 파일, 기능 체크리스트, git 커밋, 테스트 상태, 의사결정 로그, 체크포인트를 외부 상태로 남겨 다음 세션이 재구성할 수 있게 한다. 초기화 에이전트와 실행 에이전트를 분리하는 패턴도 같은 목적이다.

런타임 지속 방식 자체도 의미론이 된다. 한 연구에서 지속 상태로 학습된 Qwen3-8B를 비지속 런타임에 두자 약 80%의 에피소드에서 누락 변수 오류가 났고, 반대 조합은 약 3.5배 토큰을 썼다. “상태를 보존할지”는 구현 편의가 아니라 모델·학습 궤적·배포 런타임 간 계약이다.

근거: Anthropic / Long-running agents · Agents Learn Their Runtime

State contract 새 세션이 5분 안에 “무엇을 왜 했고 다음은 무엇인지” 복원할 수 있어야 한다.

80%·3.5배 수치는 합성 최적화 과제의 통제 실험이다. 범용 코딩 에이전트 전체에 그대로 적용되는 비율은 아니다.

T.05

멀티 에이전트는 ‘인원 추가’가 아니라 토폴로지 설계

하위 에이전트, 스킬, 핸드오프, 라우터는 서로 다른 비용 구조를 가진다. 병렬화·컨텍스트 격리·전문화가 실제 병목일 때만 멀티 에이전트가 이득이다. 반복 대화나 단일 도메인에서는 스킬과 상태 유지가 더 싸고, 다중 도메인 병렬 조사에서는 격리된 하위 에이전트나 라우터가 유리할 수 있다.

AdaptOrch는 동일 모델을 두고 과업 의존성 그래프에 따라 병렬·순차·계층·하이브리드 토폴로지를 선택해 정적 단일 토폴로지 대비 12–23% 향상을 보고했다. 핵심은 “멀티 에이전트가 더 낫다”가 아니라 과업 구조에 맞춰 실행 그래프를 선택한다는 점이다.

근거: LangChain / Multi-agent architecture · AdaptOrch · Anthropic / 2026 trends

Gate 단일 에이전트 → 도구 → 스킬 → 필요한 경우에만 다중 에이전트.

에이전트 수가 늘면 핸드오프 스키마, 중복 작업, 충돌 병합, 비용·지연, 권한 면도 함께 늘어난다.

T.06

권한 프롬프트에서 구조적 통제로

“조심해서 실행하라”는 자연어는 정책이 아니다. 최신 패턴은 과업 단계마다 보이는 도구 스키마를 줄이고, 위험 등급·허용 경로·네트워크 범위·비밀 접근을 코드로 표현한다. 샌드박스 내부에서는 자유롭게 탐색하되 경계 밖으로 나갈 때만 승인을 요청하는 방식이 생산성과 안전을 함께 노린다.

statewright는 상태 머신으로 단계별 도구를 제한해 로컬 모델 두 개의 5개 SWE-bench 하위 과제 결과가 총 10회 중 2회 성공에서 10회 중 10회 성공으로 바뀌었다고 보고했다. 방향은 설득력 있지만, 전체 2,294개가 아닌 5개 과제이며 프로젝트 제작자의 자체 실험이라는 범위를 반드시 붙여야 한다.

근거: Anthropic / Beyond Permission Prompts · statewright · Cursor / Agent sandboxing

Control plane 정책을 프롬프트가 아니라 도구 카탈로그·상태 전이·샌드박스 경계로 강제한다.

인간 승인도 모든 호출이 아니라 비가역성·금전·데이터 노출·외부 커뮤니케이션 같은 고위험 경계에 집중한다.

T.07

관측성은 운영 대시보드가 아니라 ‘하네스의 학습 신호’

트레이스는 사후 장애 분석만을 위한 것이 아니다. 어떤 컨텍스트를 봤는지, 어떤 도구에서 막혔는지, 동일 파일을 몇 번 고쳤는지, 테스트를 왜 건너뛰었는지까지 기록해 실패 유형을 집계한다. 이 집계가 다음 프롬프트·도구·미들웨어·평가셋 변경의 입력이 된다.

동시에 사람은 모든 출력을 줄 단위로 확인하는 역할에서, 목표·경계·센서·에스컬레이션을 설계하는 “on-the-loop” 운영자로 이동한다. Anthropic의 2026 보고서는 개발자가 업무의 약 60%에서 AI를 쓰지만 완전 위임 가능하다고 답한 과업은 0–20%에 그쳤다고 정리한다. 자율성보다 선택적 감독이 현재의 현실이다.

근거: LangChain / Trace analyzer · Anthropic / 2026 Agentic Coding Trends · Martin Fowler / Harness engineering

Outer loop 실패 트레이스 → 분류 → 하네스 변경 → 회귀 평가 → 점진 배포.

로그를 많이 모으는 것보다, 실패 분류와 다음 변경을 연결하는 짧은 개선 주기가 더 중요하다.

03 · Reference architecture

닫힌 루프가 되는 최소 구조.

모델은 중앙의 교체 가능한 추론 코어다. 실제 신뢰성은 앞단의 컨텍스트 선택, 옆단의 도구·권한, 뒷단의 검증·관측·상태 갱신이 연결될 때 생긴다.

01 / FEEDFORWARD

02 / EXECUTION BOUNDARY

03 / FEEDBACK

검증·트레이스·지속 상태가 다음 행동과 다음 세션을 교정한다.

ANTI / 01

거대한 단일 지시문

컨텍스트를 잠식하고 규칙의 우선순위를 흐린다. 짧은 지도와 검색 가능한 하위 문서로 분해한다.

ANTI / 02

모든 실패에 새 도구 추가

도구·예외·가드레일이 기하급수로 늘어난다. 범용 파일·검색·셸과 명확한 스키마를 우선한다.

ANTI / 03

검증 없는 자가 확신

코드를 다시 읽는 것은 테스트가 아니다. 종료 훅과 외부 센서가 실제 사양을 대조해야 한다.

ANTI / 04

기본값으로 멀티 에이전트

명확한 병렬화·격리 이득이 없으면 비용, 지연, 핸드오프 오류만 늘어난다.

ANTI / 05

프롬프트에만 둔 보안 정책

자연어 준수를 신뢰하지 말고 보이는 도구·허용 경로·네트워크·승인 단계를 코드로 강제한다.

ANTI / 06

평가셋 없는 하네스 튜닝

한 과제를 고친 변경이 다른 과제를 망가뜨릴 수 있다. 모든 변경은 반복 실행과 회귀 감시를 통과해야 한다.
