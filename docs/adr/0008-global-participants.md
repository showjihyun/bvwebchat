# ADR-0008: global 채널은 참여자 목록을 갖지 않는다

- 상태: 승인
- 날짜: 2026-08-05
- 관련 스펙: RQ-15 (참여자 목록 표시), RQ-12 (빈 room 자동 삭제), RQ-04, ADR-0004

## 맥락

RQ-15 는 *"시스템은 각 room 의 현재 참여자 목록을 표시해야 한다"* 이다. `global` 도
room 이므로(ADR-0004) 문자 그대로 읽으면 global 에도 참여자 목록이 있어야 한다.

**실제로는 영구히 비어 있다.** 2인이 접속해도 `participants` 방송이 0건이다(2026-08-05
실측). 기전은 두 경로의 비대칭이다:

| 경로 | 하는 일 |
|---|---|
| `src/server/chat/connection.ts:28` | 접속 즉시 `socket.join(GLOBAL_ROOM)` — **소켓 멤버십만** |
| `src/server/chat/room.ts:39-42` (`handleJoin`) | global 을 예약 이름으로 거부하고 **`addMember` 전에 `return`** |

그래서 `state.members` 에 `global` 키가 생기지 않고, `broadcastParticipants(io, state,
GLOBAL_ROOM)` 이 호출되는 경로가 **아예 없다**.

이 상태는 RQ-18-a(2026-08-04) 전까지 사용자에게 보이지 않았다 — global 자체가 UI 에
렌더되지 않았기 때문이다. global 을 room 목록에 올리자 **빈 참여자 칸이 드러났다.**

**이 ADR 이 필요한 이유는 그 배제가 우연이 아니라는 것이다.**
`src/server/chat/departure.ts:70-73` 이 이렇게 적고 있다:

> RQ-12 / ADR-0004 예외 2: … `GLOBAL_ROOM`은 members 순회 대상에 **애초에 등록되지
> 않으므로(RQ-15 설계 결정)** 이 루프 자체에 나타나지 않아 삭제 대상에서 **구조적으로
> 제외된다.**

즉 **"global 이 `state.members` 에 없다"는 사실 자체가 ADR-0004 예외 2(전원 종료 후에도
global 존속)의 집행 수단**이다. 그런데 그 결정이 ADR 어디에도 없다 — ADR-0004 결과 절은
RQ-12·RQ-13 예외만 나열하고, 근거는 코드 주석 두 곳(`departure.ts:70-73`,
`session.ts:287`)뿐이다.

**결정은 내려져 있었고 기록되지 않았다.** 그 상태에서 다음 사람은 빈 패널을 결함으로
읽고 서버를 고치려 든다.

## 결정

**global 채널은 참여자 목록을 갖지 않는다. RQ-15 의 적용 대상은 사용자 생성 room 뿐이다.**

클라이언트는 global 이 활성일 때 **빈 칸을 두지 않고 그 이유를 표시한다.**

## 근거

### 버린 대안 1 — 서버가 global 도 `state.members` 에 넣는다

RQ-15 를 문자 그대로 충족하고 global 참여자가 실제로 보인다. **버린 이유는 위계다.**

지금 ADR-0004 예외 2(global 존속)를 집행하는 것은 **구조**다 — global 이 순회 대상에
없으므로 삭제 루프에 **나타날 수 없다**. `members` 에 넣으면 그 보장이 사라지고
`departure.ts` 의 삭제 루프와 `handleLeave` 의 빈 room 정리에 **명시적 조건문**을
넣어야 한다. 이 저장소의 위계는 **구조 > 게이트 > 센서 > Guide** 이고, 이것은 구조를
조건문으로 내리는 변경이다.

대가도 계산했다: 조건문은 두 곳이 아니라 **세 곳 이상**이 된다(삭제 루프 ·
`removeMember` 의 `becameEmpty` 판정 · `broadcastRooms` 의 user room 유도). 각각이
빠뜨릴 수 있는 자리이고, 빠뜨리면 **global 이 사라진다** — RQ-04 가 통째로 깨지는
실패 모드다. 참여자 목록을 얻자고 감수할 위험이 아니다.

### 버린 대안 2 — 클라이언트가 자체 집계한다

`rooms`·`message` 이벤트에서 발신자를 모아 global 참여자를 추정한다. **버린 이유는
정확성이다.** 조용히 접속만 하고 발언하지 않은 사용자를 셀 수 없고, 그 목록은
*"참여자"* 가 아니라 *"최근 발언자"* 다. **이름이 실제와 다른 UI 는 빈 칸보다 나쁘다.**

### 버린 대안 3 — RQ-15 를 개정해 global 을 명시적으로 제외한다

requirements 를 고치는 것이 가장 정직해 보인다. **버린 이유는 관할이다.** RQ-15 의
문장(*"각 room 의 참여자 목록"*)은 그대로 옳고, 바뀌어야 하는 것은 *"global 이 그
'room' 에 포함되는가"* 라는 **아키텍처 판단**이다. ADR-0004 가 이미 global 을
*"예외를 가진 room"* 으로 정의했으므로 예외 목록에 한 줄 더하는 것이 관할에 맞는다.
requirements 는 무엇을 원하는지 적고, ADR 은 그것을 어떻게 성립시키는지 적는다.

## 결과

- **ADR-0004 의 global 예외가 3건이 된다** — ① 예약 이름(RQ-13) ② 전원 종료 후 존속
  (RQ-12) ③ **참여자 목록 없음(RQ-15, 이 ADR)**. ③은 ②의 집행 수단이므로 둘은
  독립이 아니다. **②를 다른 방식으로 집행하기로 하면 ③을 다시 판단해야 한다.**
- **사용자는 global 에 누가 있는지 영영 알 수 없다.** 이것이 이 결정의 실질적 대가이고,
  숨기지 않고 UI 가 말한다. 그 문구는 DESIGN.md 관할이다.
- RQ-15 의 골든(GA-19·20)은 user room 을 대상으로 하며 global 케이스를 추가하지 않는다
  — 추가하면 이 결정과 모순된다.
- **서버 변경 0.** 이 ADR 은 이미 존재하는 동작을 기록하고 UI 의 표현을 정한다.
- 나중에 후회할 수 있는 지점: **동시 접속자 수가 늘면 "global 에 몇 명 있나"가 실제
  요구로 올라올 수 있다.** 그때 답은 참여자 *목록* 이 아니라 **접속자 수**일 가능성이
  높고, 그것은 `io.engine.clientsCount` 로 `state.members` 없이 얻을 수 있다 —
  이 결정을 뒤집지 않고 답할 수 있는 길이 있다는 뜻이다. 새 RQ 가 먼저다.
