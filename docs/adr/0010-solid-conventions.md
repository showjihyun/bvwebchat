# ADR-0010: SOLID 규약 — 함수형 TypeScript 로의 번역과 집행 층위

- 상태: 승인
- 날짜: 2026-08-09
- 관련 스펙: 없음 (횡단 규약 — 모든 RQ 의 구현에 적용된다)
- 관계: ADR-0007 결정 2·3 을 **대체하지 않고 흡수·확장**한다. 그 두 규칙은
  이 문서의 DIP 축이 되고, ADR-0007 은 서버 모듈 경계의 진실 공급원으로 남는다.

## 맥락

사용자가 *"소스 코드는 SOLID 개념에 충실하게 작성되어야 한다"* 를 규약으로
요구했다. 그런데 저장소에 SOLID 를 **이름으로** 요구하는 문장이 한 줄도 없었다.
가장 가까운 것이 ADR-0007 결정 2·3(단방향 계층·순수 코어)이고, 그것만
`no-restricted-imports` 로 두 파일에 걸려 있다. 단일 책임·개방폐쇄·인터페이스
분리는 어디에도 적혀 있지 않아 **리뷰어도 코더도 근거로 쓸 문장이 없었다.**

여기서 갈림길이 하나 있다. **이 저장소에는 클래스가 0개다.**

```
grep -rn "^\s*\(export \)\?\(abstract \)\?class " src/ | wc -l   → 0
```

`interface` 27 · `type` 별칭 16 은 전부 프로토콜 payload 와 상태 shape 이고,
상속 계층은 하나도 없다. SOLID 는 OO 를 전제로 정식화된 원칙이므로, 원문 그대로
적으면 **LSP 는 적용 대상이 0인 공허참**이 되고 OCP 는 상속을 전제한 채 판정
불가가 된다. 이름만 있고 집행이 없는 규약은 지표를 지운다.

## 결정

SOLID 5원칙을 **이 저장소의 관용구(함수형 TypeScript + Socket.IO)로 번역해**
규정하고, 기계화 가능한 축은 ESLint 로 **차단**하며 판단이 필요한 축은
reviewer 가 판정한다. 번역과 집행 수단을 원칙마다 명시한다.

| # | 원칙 | 이 저장소에서의 뜻 | 집행 |
|---|---|---|---|
| 1 | **SRP** | 모듈은 **상태 소유권** 하나를, 함수는 **관찰 가능한 효과** 하나를 책임진다 | ESLint `max-lines-per-function` 60 · `max-lines` 250 (대리 지표) + reviewer |
| 2 | **OCP** | 요구가 늘 때 기존 함수의 **분기를 늘리지 않고** 함수·모듈을 더한다 | reviewer |
| 3 | **LSP** | 상속이 없으므로 **선택적 필드·유니온**에 적용한다 — 필드가 없는 값과 있는 값이 같은 수신 경로에서 같은 계약을 지켜야 한다 | 타입 체커 + reviewer |
| 4 | **ISP** | 핸들러는 **자기가 쓰는 것만** 받는다. 공용 컨텍스트 객체로 묶지 않는다 | reviewer |
| 5 | **DIP** | 단방향 계층 — 상위가 하위를 부르고 역방향 import 는 금지 | ESLint `no-restricted-imports` (계층 그래프 전체) |

### 1. SRP — 길이는 대리 지표다

**책임의 개수는 셀 수 없다.** 길이는 책임이 늘 때 함께 늘어나는 관측 가능한
축이고, 이 저장소에서 실제로 그 형태로 발화했다: RQ-04-a 에서 `handleMessage`
에 다섯 번째 책임(global 팬아웃)을 인라인으로 붙이자 `room.ts` 머리 주석의
*"handleMessage 가 네 줄로 읽히는 것이 이 분해의 목표였다"* 가 **거짓이 됐고**,
리뷰어가 그것을 SRP 위반으로 잡아 함수 추출로 되돌렸다.

**한계를 여기 적어 둔다** — 길이는 필요조건도 충분조건도 아니다. 60줄 안에서
세 가지 책임을 지는 함수는 이 게이트를 통과한다. 그 축은 reviewer 가 본다.
대리 지표를 원칙 자체로 착각하면 *"짧으니까 SRP 를 지켰다"* 가 되고, 그것은
게이트가 만들어 내는 가장 흔한 거짓말이다.

### 3. LSP — 공허참이라고 적지 않고 무엇에 적용되는지 적는다

상속이 없으므로 원문의 "파생 클래스 치환 가능성"은 대상이 0이다. 그러나 그
정신 — *같은 타입으로 선언된 값은 어디서 오든 같은 계약을 지킨다* — 은 선택적
필드에 그대로 적용된다. 실사례가 이 저장소에 있다: `ChatMessage.origin?: 'global'`
은 팬아웃 **사본에만** 붙고 원본에는 붙지 않는데, 두 값이 같은 `message`
수신 경로를 지난다. 수신 측이 `origin` 유무로 갈라져 한쪽만 처리하면 그 순간
LSP 위반이다.

### 5. DIP — ADR-0007 의 계승

계층은 ADR-0007 결정 2 가 정한 그대로다.

```
shared/types → validation·protocol → state → broadcast → session
             → room·departure → connection → createChatServer
```

실측한 import 간선이 이 선언과 **정확히 일치**하므로(2026-08-09), 그래프 전체를
`no-restricted-imports` 로 거는 데 코드 변경이 필요하지 않다. 그전까지는 이 그래프
중 `state.ts`·`validation.ts` **두 파일만** 걸려 있었다 — 선언은 8층이고 집행은
2층이었다.

**사슬의 두 끝을 빠뜨렸다가 1차 리뷰가 잡았다.** 처음 배선에서 L1(`src/shared/**`)과
L8(`createChatServer`)이 어느 블록에도 없어 `../createChatServer` 역방향 import 를
아무것도 막지 않았다 — *"계층 그래프 전체"* 라는 **문장이 집행보다 넓었다.**
문언을 좁히는 대신 집행을 넓혔고, 두 끝에 대한 음성 시험을 붙였다
(`room.ts` 에 `../createChatServer`, `shared/types.ts` 에 `../server/chat/state` 를
주입하면 각각 `exit 1`).

> **flat config 함정 하나를 기록한다.** 공통 금지(`../createChatServer`)를
> `src/server/chat/**` 한 덩어리로 **뒤에** 두면 같은 규칙 ID 에 대해 나중 블록이
> 이겨서 **앞의 계층별 patterns 가 통째로 지워진다.** 실제로 그렇게 썼다가
> `npx eslint --print-config` 로 7개 파일의 실효 규칙을 찍어 보고 잡았다.
> 공통 항목을 각 블록에 **반복**하는 것이 이 도구에서의 정답이다.

## 예외표 — 부채이지 면제가 아니다

기존 위반 6건을 `eslint-disable` 로 숨기지 않는다. `eslint.config.js` 에 **현재
값으로 고정한 override** 로 등재한다. 값을 현재치에 박는 것이 핵심이다 —
**그 파일은 더 자랄 수 없고**(래칫), 부채를 갚으면 항목을 지워 임계값이 조인다.

**핀은 파일 단위다** — ESLint override 의 단위가 파일이라 한 파일 안의 여러 함수는
그중 **가장 긴 것**으로 함께 덮인다. 따라서 아래 4개 핀이 위반 6건을 흡수한다.

| 파일 | 규칙 | 핀 | 규약 | 이 핀이 덮는 위반 |
|---|---|---|---|---|
| `src/client/useChat.ts` | `max-lines` | 293 | 250 | 파일 293줄 |
| `src/client/useChat.ts` | `max-lines-per-function` | 237 | 60 | `useChat` 237 · `:147` 화살표 92 · `:280` 화살표 61 |
| `src/client/components/ChatPane.tsx` | `max-lines-per-function` | 75 | 60 | `ChatPane` 75 |
| `src/client/components/JoinRoomModal.tsx` | `max-lines-per-function` | 64 | 60 | `JoinRoomModal` 64 |

⚠️ **래칫의 한계를 여기 적어 둔다** (1차 리뷰 major). 파일 단위 핀이므로
**`useChat.ts` 안에서는 92줄·61줄 함수가 236줄까지 자라도 통과하고, 새 함수도
그렇다.** *"그 파일은 더 자랄 수 없다"* 가 엄밀히 참인 것은 `max-lines` 축뿐이다.
함수 축의 래칫은 **파일 최댓값에만** 걸린다. ESLint 는 함수 단위 override 를
제공하지 않으므로 이 한계는 도구의 것이고, 좁히려면 그 파일을 쪼개는 수밖에
없다 — 즉 **부채를 갚는 것이 유일한 처방**이고 그것이 원장에 있는 이유다.

**위반 6건이 전부 클라이언트에 있고 서버 모듈은 하나도 없다.** 이것이 이 ADR 의
가장 강한 근거다 — 서버는 ADR-0007 이 경계를 정했고 클라이언트는 그런 문서가
없었다. 규약의 유무가 코드 모양으로 그대로 나타났다.

이 PR 에서 리팩터하지 않는다. 규약 PR 에 구현 변경을 섞으면 CLAUDE.md 의
*"스펙 항목 1개 = 브랜치 1개 = PR 1개"* 를 깨고, `useChat.ts` 는 미이행 결함
(RQ-04 v1.2 세 번째 불릿 — resume 뒤 room 이력 복원)을 안고 있어 그 결함을 닫는
작업과 분해가 같은 파일에서 충돌한다. 부채는 `docs/progress.md` 원장에 있다.

## 근거

**버린 대안 1 — SOLID 를 원문 그대로 적는다.** LSP 가 공허참이고 OCP 가 상속을
전제해 둘 다 판정 불가가 된다. 규약이 판정 불가면 리뷰어는 그것을 인용할 수
없고, 인용되지 않는 규약은 없는 규약이다.

**버린 대안 2 — 새 센서 스크립트(가칭 `solid-lint`).** ESLint 가 이미 하는 일과
중복이고, 통제면을 하나 더 늘린다(안티패턴 02). 새 게이트는 음성 시험 의무도
따라온다(`harness/recurrence.md` R2). ESLint 는 `scripts/check.mjs` 의 lint 스텝과
CI `gate` 잡에 **이미 배선돼 있어** 새 표면이 0이다.

**버린 대안 3 — reviewer 축만 둔다.** Guide 층위여서 리뷰어가 놓치면 그대로
통과한다. 우선순위가 **구조 > 게이트 > 센서 > Guide** 인데, 기계화 가능한 축을
가진 채로 Guide 를 택하는 것은 그 순위를 거꾸로 적용하는 것이다.

**버린 대안 4 — 지금 전부 리팩터해 예외 0으로 만든다.** 위 예외표 절 참조.

**버린 대안 5 — 임계값을 현재 최대치로 캘리브레이션(함수 80 · 파일 450).**
즉시 초록이고 예외표가 필요 없다. 그러나 현재 코드가 곧 상한이 되어 실질
제약이 사라진다 — 새 코드가 446줄까지 자라도 통과한다. **초록을 사는 대신
규약을 잃는 교환**이다.

## 결과

- 새 코드가 함수 60줄·파일 250줄을 넘으면 `check.mjs` 의 lint 스텝과 CI `gate`
  가 막는다. 예외는 위 표의 6건뿐이고 전부 현재값에 고정돼 자랄 수 없다.
- **후회할 수 있는 지점: 60 과 250 은 임의의 수다.** 55 가 아니라 60 이어야 할
  원리적 근거가 없다. 실제 근거는 *"이 값에서 위반이 6건이고 그건 갚을 수 있는
  크기"* 라는 것뿐이며, 코드가 자라면 이 근거는 다시 재야 한다. 값을 **올리는**
  방향으로 고치는 것은 이 ADR 을 대체하는 새 ADR 로만 한다 — 게이트가 빨갛다는
  이유로 임계값을 올리는 것은 실패 테스트를 지우는 것과 같은 종류의 행위다.
- 클라이언트에는 아직 ADR 이 없다. 이 규약이 클라이언트 경계 문서의 부재를
  **드러내지만 메우지는 않는다** — 위반 6건이 전부 거기 있는 것이 그 증거다.
