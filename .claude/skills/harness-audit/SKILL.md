# Harness Audit — 하네스를 바꾸기 전에 통과하는 문

하네스 변경은 **측정 도구를 바꾸는 일**이다. 측정 도구를 재보지 않고 바꾸면
그 뒤의 모든 숫자가 무엇을 뜻하는지 알 수 없게 된다. 평가셋 없는 하네스 튜닝이
안티패턴 06인 이유다.

이 스킬은 두 가지를 한다: **현재 상태를 재고**, **변경 제안을 1건으로 좁힌다.**

## Phase 0: 단계 진입

```
python harness/phase.py enter HARNESS
```

`HARNESS` 단계는 `src/**`·`tests/**`·`specs/**` 쓰기를 막는다
(정확한 경로 목록은 `python harness/phase.py show` — 값을 여기 옮겨 적지 않는다) —
CLAUDE.md의 "ADR·하네스 전용 PR" 카브아웃이 산문에서 구조로 승격된 지점이다.
하네스 PR에 기능 코드가 섞이는 일이 **물리적으로 불가능**해진다.

## Phase 0-1: 운영 순서 — 전이 → 커밋 → 평가

단계를 전이하면 체크포인트가 생긴다. **평가(`eval-b`·`resume-test`)는 격리
워크트리에서 돌고 워크트리는 커밋된 것만 본다.** 따라서 전이 직후 평가를 돌리면
`checkpoint_uncommitted` 로 반드시 실패한다.

```
python harness/phase.py session --done "…" --next "…"   ← 전이 게이트가 신선도를 본다 (R6)
python harness/phase.py enter <PHASE>
git commit -- .harness/state          ← 이 줄을 빠뜨려 4회 반복했다 (recurrence R4)
node scripts/eval-b.mjs ...
```

`eval-b` 의 에러 메시지가 이미 증상을 정확히 말하고 있었지만(*"커밋되지 않은 내구
기록은 다른 머신에서 읽히지 않는다"*) **순서가 절차로 적혀 있지 않았다.**
메시지는 증상을 말하고 절차는 순서를 말한다 — 둘은 다르다.

**그런데 이 절차를 적은 다음 실행에서 4번째가 났다.** 원인은 망각이 아니라
**R3(커밋 오염 → `git commit -- <경로>` 만 쓴다)와 정면으로 당긴다**는 것이다 —
pathspec 을 좁게 쓸수록 상태 파일이 자동으로 빠진다. 그래서 이제 **Guide 가 아니라
게이트**가 잡는다: `eval-b` 가 시작 시 `.harness/state` + `HASH_GLOBS` 미커밋을
검사해 첫 케이스 전에 `exit 3` 한다. 이 절차는 그 게이트를 안 만나는 방법이지
게이트를 대신하지 않는다.

`HASH_GLOBS` 까지 보는 이유(5차 재리뷰 B-k): `inputsHash()` 는 **워킹트리**를 읽는데
케이스는 **HEAD 워크트리**에서 돈다. 하네스 입력이 미커밋이면 평가는 그것을 보지 못한
채 아티팩트에 그 해시를 박고, 나중에 커밋하면 `--verify-artifact` 가 해시 일치로
통과한다 — **한 번도 평가되지 않은 변경이 `track_b_passing` 을 지나간다.**

3번이 가장 중요하다. **테스트 없는 게이트는 연극이다.** 훅이 조용히 죽어 항상
allow를 반환하는 상태와 정상 동작하는 상태는 이 검사 없이 구별되지 않는다.
필수 단언 하나: `settings.json`이 참조하는 훅 파일이 실재하는가.
(2026-07-27 이 저장소에서 훅 삭제와 재배선 사이의 창에 모든 에이전트의
Write/Edit이 죽었다. 정책 거부가 아니라 훅 파손이었고, 둘은 에러 메시지만으로
구별되지 않았다.)

### 센서 카탈로그 대조 절차

`harness/sensor-catalog.md`의 각 행을 실제 배선과 하나씩 맞춘다. 표를 읽는 것이
아니라 **양방향으로** 본다.

1. 카탈로그의 ✅ 행 → 그 강제 수단이 실재하는가? (`settings.json`의 hooks 배열,
   `.github/workflows/`의 스텝, `phase-matrix.json`의 guards, `scripts/`의 파일)
2. 실재하는 강제 수단 → 카탈로그에 행이 있는가? (없으면 **문서화되지 않은 게이트**다.
   에이전트가 이유를 모른 채 차단당한다.)
3. 🔄·⬜ 행 → 아직도 그 상태가 맞는가?

불일치는 전부 보고서에 적는다. 카탈로그를 조용히 고치지 않는다 — 불일치 자체가
발견이고, 그것이 이 감사의 산출물이다.

## Phase 3: 변경 제안 — **정확히 1건**

발견이 여러 개여도 제안은 하나다. 이유:

- 하네스를 한 번에 여러 곳 바꾸면 **어느 변경이 어느 효과를 냈는지 분리되지 않는다.**
  그 순간 다음 감사가 근거를 잃는다.
- 게이트가 많아지는 속도는 게이트가 신뢰를 잃는 속도와 같다. 한 번에 하나면
  각각이 실전에서 검증될 기회를 갖는다.

제안에 반드시 포함할 것:

1. **먼저 물을 것 — 이 실패를 구조로 불가능하게 만들 수 있는가?**
   우선순위는 **구조 > 게이트 > 센서 > Guide**다. `phase-matrix.json`의
   `write_deny` 한 줄로 막을 수 있는 것을 새 센서로 만들면 실패는 계속 일어나고
   관측만 늘어난다.
2. 무엇을 **지울지**. 센서를 더하면서 아무것도 안 지우면 anti-02(통제면 증식)로
   간다. 지울 게 없다고 판단했으면 그 판단의 근거를 적는다.
3. **새 게이트라면 음성 시험을 같은 커밋에 넣었는가** *(recurrence R2, 처방 후 2회 어김)*

   *"테스트 없는 게이트는 연극이다"* 를 이 저장소는 훅에 대해 선언해 놓고 신설 게이트
   셋 중 둘에 적용하지 않았다. 두 회차 연속 지적받았다. 판정을 **인자로만 하는 순수
   함수**로 분리하고 합성 케이스를 붙인다(`judgeRecurrence` · `judgeDirtyPaths` ·
   `session_is_stale` 이 그 형태다).

   **차단 쪽 케이스에 `통과값 + 부정어` 형태를 반드시 넣는다.** 두 번의 우회가 모두
   그 형상이었다 — `미완료`(= `완료` + 부정 접두), `완료 예정`(= `완료` + 미래).
   통과해야 할 값만 시험하면 이 계열은 영원히 안 잡힌다.

4. 실패했을 때의 에러 메시지 초안 — **고치는 법이 들어 있는지**가 채택 조건이다.
   그리고 **판정을 종료 코드로 내는지**. 오류를 출력하고 `exit 0`을 반환하면
   그건 센서가 아니라 로그다(운영 규칙 5-1). 의도적으로 비차단이면 왜 항상 0인지를
   헤더에 적는다.
5. **새 스크립트가 R2/R3 명령을 `spawnSync`로 부르는가.** 등급 분류는 Bash
   **도구 표면**에만 걸린다 — 스크립트는 도구 표면이 아니므로 어떤 등급도 보지
   않는다. 부른다면 그 호출이 무엇을 되돌릴 수 없게 만드는지 제안서에 적는다.
   2026-07-27에 `git worktree remove --force`가 정션을 따라가 `node_modules`를
   파괴해 저장소의 모든 검증이 멈췄다 — **적대적 우회가 아니라 우리가 커밋한
   정직한 코드**였다.
6. **이 변경이 거짓으로 만드는 문장이 있는가 — 역추적 필수** *(recurrence R1, 9회 반복)*

   바꾼 **정책값·경로·기본값**을 `rg` 로 전수 검색해 그것을 **인용하는 문서**를 찾는다.
   찾은 것은 **같은 커밋에서** 고친다.

   ```
   rg -n "미지 접두사|unknown_prefix|ask" --glob '!node_modules' docs/ harness/ .claude/ scripts/
   ```

   왜 필수인가: 이 저장소는 같은 실패를 **9번** 냈다. 매번 **변경은 정직하게
   기록했다**(`tool-risk.json`·changelog). 없었던 것은 **그 기록을 근거로 쓰는
   다른 문장을 찾아 고치는 단계**다. 그 둘은 다른 작업이다.

   *(2026-07-28 정정)* 한때 *"C2 는 절충이라 센서로는 답이 없다"* 고 적었는데
   **틀렸다.** C2 의 `--pr` 축소는 **두 축**이고 독립이다 — 게이트 범위를 좁히는 것은
   의존 축이고, 실패가 샌 구멍은 **문서 축**(*"이 PR 이 문서를 동행시켰으면 면제"*)이었다.
   **동행은 "건드렸다"는 뜻이지 "의존보다 나중이다"는 뜻이 아니다.** 그 한 줄을 지우자
   의존 축은 그대로인 채 C2 가 즉시 발화했다. **판정 주체는 이제 C2(센서)** 이고 이
   역추적 질문은 보조다. **"절충이라 답이 없다"고 적는 순간 다시 볼 이유가 지워진다** —
   한 칸 내려가기 전에 위 칸의 처방을 **코드 수준까지** 써 보라.

7. **처방을 미루려 한다면 그 근거를 한 줄 명령으로 검증했는가** *(recurrence R11, 3회)*

   *"이것은 별도 PR 이어야 한다"* · *"같은 파일이라 함께 배선해야 한다"* 같은 유예 근거는
   **재보기 전까지 근거가 아니라 인상이다.** 실제로 나눠 보라 — 세 번 다 나눌 수 있었다.
   `policy-lint` P11 이 이미 이것을 차단하지만, **P11 이 물기 전에 스스로 재는 것**이
   이 항목의 실질이다.

8. `docs/harness/changelog.md` 항목 초안 (날짜·변경·대상·사유).

여러 개를 제안하고 싶으면, 그것은 이 감사를 여러 번 돌려야 한다는 뜻이다.

## Phase 4: 종료

1. `docs/harness/changelog.md`에 기록 — `HARNESS→REVIEW` 전이의
   `changelog_updated` 가드가 이 파일의 변경을 요구한다.
2. 트랙 B 결과를 커밋 (`evals/results/track-b/<sha>.json`) —
   `track_b_passing` 가드가 아티팩트를 요구한다.
   **부분 실행을 썼으면 `carried_from` 이 어느 케이스에 붙었는지 보고서에 적는다.**
   입력 해시가 같으면 결과는 유효하지만 **어느 실행의 결과인지는 다르고**, 그 구별을
   리뷰어에게 넘기는 것이 아티팩트의 일이다.
3. `python harness/phase.py enter REVIEW` → `review-gate` 스킬.
